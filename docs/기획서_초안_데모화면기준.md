## 작성 원칙

- **데모에 있는 것만 씁니다.** 기획서에 쓴 기능은 데모에서 보여 줄 수 있어야 하고, 이번 버전에서 뺀 기능(현장 판단 학습·선호모델)은 쓰지 않습니다.
- **분량은 핵심 흐름에 몰아줍니다.** 대표 사례 흐름(⓪~⑦) 60%, 보조 기능 25%, 데이터·성과·한계 15%가 기준입니다.
- **숫자에는 출처를 붙입니다.** 모든 수치 옆에 "합성 데이터 대표 사례 실행 결과" 또는 "합성 환경 자동 실험"을 밝히고, 실증 목표와 섞지 않습니다.
- **캡처 아래에는 "합성 데이터 기반 프로토타입"을 적습니다.**

## 2.3 활용 시나리오 및 화면 구성

StowSync는 도착이 늦어지는 트럭을 미리 알고, 기존 적치 계획이 문제가 되기 전에 플래너가 근거를 보고 위치를 바꾸도록 돕습니다. 데모는 컨테이너 20개(초기 적치 12개, 이후 반입 8개, 선박 2척) 가운데 대표 컨테이너 SYNC2600013(OCEAN HARMONY, 일반 드라이, 선적 순서 #6) 하나를 도착 정보 변화부터 본선 인출까지 따라갑니다. 대표 컨테이너가 도착하는 09:49에는 같은 블록에서 트럭 3대가 함께 하차를 기다리므로, '어디에 놓을까'와 함께 '어떤 순서로 내릴까'를 비교합니다.

| 단계 | 입력 | 처리 | 화면에서 보이는 결과 |
| --- | --- | --- | --- |
| ⓪ 관제 | 20개 화물의 예약·ETA·선적 순서 | 지연 도착 × 선적 상위 등 검토 순위를 매김 | 현황판과 검토 순위, 대표 컨테이너가 1위로 뽑힌 이유 |
| ① 상황 확인 | 반입 예약(09:15–09:25), 운송 진행에 따른 ETA 갱신 | 게이트 도착 예상과 CY 하차 가능 시점을 나눠 계산 | 09:25 갱신에서 ETA가 09:20 → 09:44(약 24분) 늦어졌다는 문장 설명. 올컨e·Port-i·TOS 출처 카드 |
| ② 문제 확인 | 현재 야드 적치 상태, TOS 모의 인출 순서 | 기존 계획 위치(A1-02-02)에 대표보다 먼저 인출할 화물이 있는지 검사 | "기존 계획대로 놓으면 먼저 실을 #4를 가로막아 인출 때 다시 옮겨야 합니다", 3D에 기존 계획 위치 표시. 문제가 없으면 없다고 표시 |
| ③ 대안 비교 | 대기 트럭 3대(A·B·C), 선박 상태, ETA 범위, 공간·하중·화물 제약 | 대기 트럭의 처리 순서(순열)마다 같은 도착 표본 8개로 60분을 굴려 비교. 위치는 순서대로 제약을 만족하는 후보 중에서 정함 | 상위 3안과 기준(도착순 + 기존 계획 위치) 대비 추가 이동 작업시간·트럭 대기·인출 지연(분, 표본 범위), 야드 전체 예상 재취급(7.0 vs 8.0), 계산 사유, 2D 장치장 미리보기, 민감도(81조합 중 1순위 유지 수) |
| ④ 승인·보류 | 담당자의 선택, 사유(선택 사항) | 승인 직전에 대기 상태·입력 버전·60초 유효시간·특수 화물 확인을 다시 검사 | 체크 목록 후 모의 승인. 보류는 별도 분기로 기록하고 실행하지 않음 |
| ⑤ 현장 안내·실행 | 승인한 순서·위치 | 모의 크레인이 그 순서대로 하차하고 이동 로그를 남김 | 3D 재생(이동 전 → 이동 중 → 완료), 올컨e 기사 안내 미리보기, 본선 인출까지 이어서 확인 |
| ⑥ 계획 변경 대응 | Port-i 접안 30분 앞당김(모의) | TOS 인출 시각을 바꾸고 기존 결정을 재평가 | "현재 위치를 유지합니다"와 그 이유 |
| ⑦ 결과 확인 | 결정 직전 상태 | 같은 상태를 복제해 '기준(도착순·계획 위치)'과 '승인한 순서·위치'를 같은 사건·규칙으로 끝까지 실행 | 야드 전체 추가 이동 8회 → 7회, 대표 컨테이너 재이동 1회 → 0회, 두 갈래 3D 재생 |

화면 상단에는 대표 컨테이너 요약(번호·화물·상태·예약·ETA·선적 순서·위치)과 진행 체크리스트(도착 정보 확인 → 대안 비교 → 승인 또는 보류 → 작업 완료 → 결과 확인)가 항상 보입니다. 체크리스트는 화면을 열었다는 이유만으로는 채워지지 않고, 실제 처리 사건에 따라서만 완료됩니다.

**최종 결정은 사람이 합니다.** 시스템은 대안과 근거를 제시할 뿐 담당자의 선택을 채점하거나 자동으로 학습하지 않으며, 승인·보류·사유는 중립적인 작업 이력으로만 남습니다.

**가정과 불확실성.** 비교에 쓰는 비용 가중치(추가 이동 작업시간 1, 트럭 대기 0.5, 인출 지연 2, 가로막힘 1쌍 60초)는 현장 자료로 보정하지 않은 가정값이며, 도착 예측도 합성 이력 기반이라 불확실성을 표본 범위로 함께 표시합니다. 대표 사례에서는 가중치와 표본 수를 81가지로 바꿔도 같은 순서가 1순위였지만, 이는 한 장면에 대한 확인일 뿐입니다. 시드 20개·여러 조건의 자동 실험에서는 제안 정책이 트럭 대기와 인출 지연을 대체로 줄였으나 총 추가 이동은 조건에 따라 늘기도 했으므로(120조건 중 53조건 증가), 효과는 실데이터 실증으로 확인할 과제로 제시합니다.

| 기능(데모 메뉴) | 무엇을 하나 | 왜 필요한가 |

| 위험물·환적 검토 | 위험물은 모의 전용 구역 후보만, 환적은 연결 선박을 보여 주고 담당자 확인 후에만 승인합니다 | 특수 화물을 일반 화물과 같은 기준으로 승인하지 않게 합니다 |
| 2×2 예외 대응 | 조기·지연 × 선적 상위·하위로 현재 상황을 분류하고 검토 원칙을 보여 줍니다 | 상황을 설명하는 분류이며, 위치를 고정하는 규칙은 아닙니다 |
| 변경·승인 | 승인한 작업을 3D로 재생하고, 계획이나 야드가 바뀌면 기존 추천을 만료시키며, 같은 추천은 한 번만 실행합니다 | 오래된 추천으로 실행하거나 같은 작업이 두 번 나가는 것을 막습니다 |
| 기사 안내·알림 | 승인한 하차 지점만 기사 화면에 보여 주고, 일정 변경은 역할별로 나눠 알립니다 | 기사에게 야드 전체 정보를 주지 않고 필요한 것만 전합니다 |

화면은 흰 바탕에 주황(#ED6B2C) 강조이며, 주황 글자는 대비 4.5:1을 넘도록 더 진한 주황을 씁니다. 3D 야드의 색 의미는 모든 화면에서 같습니다. 남보라는 일반 화물, 빨강은 인출 순서를 방해하는 화물, 주황은 대표 컨테이너, 반투명 초록은 추천 위치, 남색 화살표는 승인된 이동 경로, 남색 테두리는 기존 계획 위치입니다. 위험물은 색이 아니라 ⚠ 표시로 구분합니다.

## 2.4 AI/데이터 활용 및 구현 구조

데모는 기존 시스템의 정보 6종을 합성 데이터로 대신하고, 실제 연계는 협의가 필요한 상태입니다. 새 기능을 만들기보다 이미 있는 정보를 연결하고, 부족한 예측·비교 기능을 보완하는 것이 제안의 범위입니다.

| 데이터 | 쓰임 | 데모의 대체 데이터 | 실제 확보 방안 |
| --- | --- | --- | --- |
| 반입 예약·운송 진행 | 예약 구간, 출발·구간 통과 | 합성 예약과 ETA 갱신 이력 | 올컨e 예약·운송 진행 정보 연계 협의 |
| 실제 도착 이력 | 게이트 도착과 CY 하차 가능 시점 | 합성 게이트 기록 | 터미널 게이트 기록(TOS) |
| 야드 현황 | 슬롯별 적치, 높이·하중 | 2개 블록 · 48슬롯 · 크레인 2대 | TOS 야드 현황 조회 |
| 선박 일정 | 작업 시간대, 반입 마감 | Port-i(모의) 일정 | BPA Port-i |
| 개별 작업계획 | 컨테이너별 인출 순서, 계획 버전 | TOS 모의 작업계획 | TOS 작업계획(선사·터미널 협의) |
| 판단·실행 기록 | 승인·보류·사유, 실제 이동 | 시연 세션 기록 | 본 모듈 기록 + TOS 작업 실적 |

선박 일정(Port-i)은 작업 시간대를 알려 줄 뿐, 개별 컨테이너의 선적 순서는 TOS 작업계획에서 받습니다.

**처리 순서**

1. **입력 수집·정합성 검사:** ID·시각·계획 버전을 맞추고, 그 시점에 알 수 있는 정보만 씁니다. 미래의 실제 도착시각은 추천에 넣지 않습니다.
2. **도착 예측:** 예약과 운송 이력으로 ETA 구간(중앙값과 범위)을 내고, 게이트 도착과 CY 하차 가능 시점을 따로 계산합니다.
3. **후보 탐색:** 공간·높이(4단)·하중·위험물 구역 제약을 통과한 위치만 후보로 둡니다. 제약은 점수와 바꾸지 않는 필수 조건입니다.
4. **유지안 대비 비교:** 앞으로 60분 동안 가능한 도착 상황 8가지를 모든 후보에 같이 적용해 재취급·선작업·대기·지연을 계산합니다. 기존 계획 유지는 항상 비교 대상에 들어갑니다.
5. **관리자 승인:** 승인 직전에 최신 상태를 다시 확인하고, 바뀌었으면 추천을 만료시킵니다.
6. **기존 작업 체계 반영·결과 기록:** 승인한 작업을 모의 실행하고, 하차 지점을 기사에게 안내하며, 예상과 실제를 이력으로 남깁니다.

AI는 도착 예측(2단계)에, 표본 기반 비교 계산은 후보 비교(4단계)에 씁니다. 현재 ETA는 합성 이력 기반 규칙 모델이며, 실데이터 연계 후 오차 검증이 필요합니다.

## 2.6 성과지표와 검증

핵심 지표는 **총 추가 이동 = 재취급 + 선작업**이며, 최초 적치와 정상 인출은 따로 셉니다. 이동이 줄어도 대기가 늘 수 있어 트럭 대기, 인출 지연, 미완료·마감 예외를 함께 봅니다.

### 대표 사례: 같은 사건의 두 갈래(합성 데이터 실행 결과)

결정 직전 상태(09:49)를 복제해 두 안을 각각 끝까지 실행했습니다. 실제 도착 사건·화물·장비 조건은 같고, 하차 순서·위치만 다릅니다.

| 지표 | 기준(도착순 · 계획 위치) | 승인한 순서(A → C → B) |
| --- | --- | --- |
| 야드 전체 총 추가 이동(회) | 8 | 7 |
| 대표 컨테이너가 다시 옮겨진 횟수 | 1 | 0 |
| 대표 컨테이너 인출 지연(분) | 9.7 | 8.0 |
| 평균 인출 지연(분) | 14.4 | 13.1 |
| 평균 트럭 대기(분) | 2.2 | 1.9 |
| 미완료·마감 예외(개) | 0 | 0 |

승인한 순서는 이 장면에서 트럭 대기를 늘리지 않고 추가 이동을 1회 줄였습니다(예상 7.0 vs 8.0, 실행 후 7 vs 8). 한 장면의 값이므로 일반적인 개선 효과로 쓰지 않습니다.

### 정책 실험실: 별도 자동 실험(합성 환경, 컨테이너 40개)

대표 사례와 별개로 같은 합성 사건에 세 정책을 자동으로 적용한 결과입니다. 앱 화면은 시드 7 한 번 실행(예약 기반 30 / ETA 기반 33 / ETA + 선작업 27회)을 보여 주지만, **한 번 실행 결과는 시드에 따라 순위가 뒤집히므로** 기획서에는 다조건 결과를 씁니다.

시드 20개 × 초기 점유율(0.35·0.5) × ETA 오차(5·10·20분) = 120조건, ETA + 선작업 vs 예약 기반, 같은 시드끼리 비교:

| 지표 | 줄어든 조건 | 같음 | 늘어난 조건 | 조건별 평균 차이 |
| --- | --- | --- | --- | --- |
| 총 추가 이동 | 50 | 17 | 53 | -0.5 ~ +0.6회 |
| 평균 트럭 대기 | 91 | 0 | 29 | -0.7 ~ 0.0분 |
| 평균 인출 지연 | 82 | 0 | 38 | -2.9 ~ -0.9분 |

**제안 정책은 트럭 대기와 인출 지연을 대체로 줄였지만, 총 추가 이동은 일관되게 줄지 않았습니다(120조건 중 53조건 증가).** ETA 오차가 20분으로 커지면 대기·지연 개선도 거의 사라집니다. 점유율 0.65는 야드가 가득 차 대부분의 화물이 처리되지 못해 비교에서 뺐습니다. 자세한 표는 `docs/수치_점검_보고.md`에 있습니다.
